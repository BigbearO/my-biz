二、已确认的技术决策（按你拍板的来）
令牌模式：reference token（不透明令牌），不走 JWT 验签模式

你明确不想走"网关验签 JWT"那套，要的是易于管理、能踢人的 token 模式。
复用 Keycloak 发的 token，但网关把它当 opaque 串

Keycloak 颁发的 access_token（本身是 JWT）被当作不透明随机串；网关不验签、不解析，只拿 sha256(token) 去 Redis 查用户态。
JWT 的验签与声明解析（sub / roles / jti / exp）只发生在外部登录/令牌服务端，不在网关。
网关彻底移除 oauth2 / JWT 依赖

删除 spring-security-oauth2-jose、NimbusReactiveJwtDecoder、KeycloakJwtTokenParser。
网关运行时零 Keycloak 依赖、零 oauth2 依赖：Keycloak 挂了也不影响已登录用户鉴权（只要 Redis 在）。
网关职责边界不变（沿用原设计）

网关只做：查 Redis 取 userId + roles → casbin enforce(role, path, method) → 200/401/403。
不管理角色/权限/用户，没有管理接口。
权限模型不变：casbin 仅 p 规则

model.conf 仅 p = sub, obj, act，无 g；用户→角色从 Redis 来，不进 casbin。
外部系统写 casbin_rule 的 p 行 + Redis Pub/Sub 广播，网关 Watcher 热更新（角色权限变更即时生效）。
踢人粒度：单 token + 按用户全端

单 token：DEL / 标记 status=revoked 该条 Redis 记录。
按用户全端：维护 user:{userId}:tokens（Set），批量删 + 清集合。
三、关键约定与边界
胶水约定（最重要）：casbin 的 p.sub（角色 key）必须等于 Keycloak 的 Realm Role 名。这是连接"Keycloak 角色"与"casbin 权限"的唯一桥梁。
Redis 用户态：Key = {prefix} + sha256(token)；Value = { userId, roles[], status, exp, deviceId, issuedAt }。读不到 / status=revoked / 过期 → 401。
App 自注册默认角色：注册后挂 app_user，业务侧给 app_user 配 p 规则。
管理系统两个写入面：① 通过 Keycloak Admin API 管账号与角色分配；② 写 casbin_rule 的 p 规则 + publish 热更新。
登录/令牌服务职责（外部）：调 Keycloak 换 token → 验签解析 JWT 取 userId/roles → 写 Redis（并加入 user:{userId}:tokens 集合）。
四、风险与注意（落盘时会写进文档）
全端踢的彻底性：只删 Redis 不够——用户若持未过期 refresh_token 会续命。彻底下线须配合 Keycloak Admin API 撤销该用户会话/refresh token。文档会注明此为两层动作。
网关缓存窗口：本地 Caffeine 若缓存 token→userInfo，踢人后有短暂放行窗口；建议缓存 TTL 设短，或踢人时经 Pub/Sub 清各节点 Caffeine（同 casbin watcher 思路）。
Redis 高可用：网关鉴权完全依赖 Redis，须 Cluster/Sentinel（架构.md 已规划）。
Token 安全：token 用 sha256 作 key（不存明文 token）；全程 HTTPS；短 TTL + 可吊销 refresh token。
