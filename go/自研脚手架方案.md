# 自研脚手架方案(kratos v3)

> 2026-11-07。目标:以 **kratos 官方组件为底**,替代 gowind(tx7do 不升级 v3)/kratos-kit(太重、耦合),
> 做一个能直接写业务的自用脚手架。鉴权在网关完成,脚手架**不做任何 auth**。
> 前置调研:`kratos-v3.md`(v2→v3 事实校正与 gow 治本方案)、`v2ToV3.md`、`wind迁移v3.md`;

## 2. 总体形态(三工件)

```
my-go-admin/
├── wind-template/            ← 工件① 模板仓(被官方 kratos new -r 克隆)
│   ├── pkg/bootstrap/        ← 工件② 胶水代码(随模板复制进每个项目,不是依赖库)
│   ├── api/                  ← buf workspace + proto(默认位置)
│   ├── app/admin/service/    ← 示例服务(作为活样板)
│   ├── pkg/                  ← 共享包(serviceid 等)
│   ├── Makefile + app.mk
│   └── .scaffold.example.yaml
└── wind/                     ← 工件③ 自研 CLI(fork 自 go-wind-toolkit/gowind)
    ├── cmd/wind/             ← new / proto / api / ent / generate / doctor
    └── pkg/...               ← gowind 引擎原样保留 + 重写的模板
```

**为什么胶水是复制不是库**:kratos-v3.md §4.8 的全部痛苦(未发布模块、replace 覆盖率、go.work、
占位版本)都源于"本地改过的库怎么被生成项目引用"。复制分发把这些一次性消灭;
代价是升级要靠 CLI 重覆盖(`wind upgrade`,后置功能),对内部脚手架完全划算。

## 3. 工件① 模板仓 `wind-template`

### 3.1 目录布局(monorepo 多服务,以 gow 模板为骨、v3+官方组件为肉)

```
wind-template/
├── api/
│   ├── buf.yaml                 # workspace,deps: googleapis / kratos apis / gnostic / pagination
│   ├── buf.gen.yaml             # Go 生成:protoc-gen-go / go-grpc / go-http(v3)/ validate / openapi
│   ├── buf.gen.ts.yaml          # 其他语言按需拆模板(默认注释)
│   ├── protos/                  # ★ proto 默认位置:<module>/service/<version>/<model>.proto
│   │   └── helloworld/service/v1/greeter.proto
│   └── gen/go/...               # go_package_prefix 重定向到本模块
├── app/
│   └── admin/service/
│       ├── cmd/server/
│       │   ├── main.go          # bootstrap.RunApp(ctx, newApp)
│       │   ├── wiring.go        # ★ 手写装配:四层分节 + 全部 register:* 锚点 + LIFO cleanups
│       │   └── assets/          # embed openapi.yaml
│       ├── internal/
│       │   ├── data/            # ent/gorm client + <model>_repo.go
│       │   ├── service/         # <model>_service.go(实现 proto Server)
│       │   └── server/          # grpc_server.go / rest_server.go(中间件+param/route 锚点)
│       └── configs/             # bootstrap/server/data/trace.yaml
├── pkg/
│   ├── bootstrap/               # ★ 工件②,见 §3.2
│   └── serviceid/
├── Makefile                     # 递归 app/*;目标 init/api/openapi/gen/build/test/lint
├── app.mk                       # 每服务 Makefile 只 include 它
├── Dockerfile / .env / .scaffold.example.yaml
```

### 3.2 工件② `pkg/bootstrap` 装配链(全部官方组件)

```
main.go → bootstrap.RunApp(ctx, newApp)
 1. 读本地 configs/bootstrap.yaml:appInfo(project/appId/version/instanceId)
    + nacos(addr/namespace/group/dataId) + 本地配置目录
 2. 配置:官方 config 包,file source(本地兜底)+ nacos source 合并
    → conf 结构体(server/grpc/rest、data、trace、logger),支持 env 覆盖
 3. logger:slog 多路 handler
    = slog.JSONHandler(stdout, 本地保留)                ← 开发期看得到
    + otel.NewHandler(appId, WithLoggerProvider(lp))    ← OTLP 转发,自动带 trace_id/span_id
    外层再包 WithFilter(脱敏 password/token/secret)
    log.SetDefault(l.With("service.id",...,"service.version",...))
    其中 lp = OTLP LoggerProvider(otlploggrpc exporter + resource(service.*)),退出时 Shutdown flush
 4. tracer:OTLP TracerProvider(otlptracegrpc exporter,ParentBased 采样)
    + otel.SetTextMapPropagator(TraceContext+Baggage)
 5. registrar:registry/nacos → kratos.Registrar;服务名 = project/appId
 6. newApp(ctx):构造 grpc/rest server
    中间件仅 4 个:recovery + logging + validate + tracing.Server()   ← 无 auth
 7. app.Run();defer 逆序 shutdown(tracer flush → logger flush → deregister)
```

客户端服务发现:`discovery.New(nacosRegistry)` + `kratos selector`,标准官方姿势。

# configs/bootstrap.yaml —— 本地,唯一必须的本地文件

  project: my-biz

### 3.4 proto 共享机制:多语言共用 + 目录默认/可指定

> 前提:同一批 proto 源文件会在 **Go / TS / Java / Dart** 等多种语言间共用,
> 因此 proto 目录可能是一个**跨项目公共目录**(独立 proto 仓的 checkout、公司级共享目录)。
> 方案:**模板保持 gow 同款的默认位置,同时允许配置把 proto 源指到任意位置**;
> 两种模式下 proto 文件内容与布局约定完全相同,差别只在落盘位置与生成路由。

**1)目录解析(所有 proto 相关命令统一入口:先读项目根 `.scaffold.yaml`)**

```yaml
# .scaffold.yaml —— wind new 生成,可手改
module: github.com/yourname/your-project
proto_dir: api/protos          # ★ 默认:模板自带,与 gow 完全同款(api/ 为 buf workspace)
# proto_dir: ../proto          # 可选:公共 proto 目录(独立仓 checkout,相对路径)
# proto_dir: /srv/company-protos   # 可选:绝对路径
```

| 模式 | proto 源与 buf 配置归谁管 |
|---|---|
| **默认模式**(项目内) | 模板自带 `api/protos/`(布局约定 `<module>/service/<version>/<model>.proto`)+ `api/buf.yaml` + `api/buf.gen.*.yaml`,项目自持 |
| **外置模式**(项目外) | `buf.yaml` / `buf.gen.*.yaml` 放在公共目录(公共仓自己管、自己演进);本项目 `.scaffold.yaml` 只记录位置;buf 以公共目录为 workspace 运行 |

**2)多语言生成路由(按语言拆 `buf.gen.*.yaml`)**

| 语言 | 模板 | 生成物去向 |
|---|---|---|
| Go | `buf.gen.yaml`(默认启用) | **始终写回当前 Go 项目** `api/gen/go/`(`go_package_prefix` 重定向到消费方模块;外置模式下 buf 用 `-o` 指回项目) |
| OpenAPI | `buf.gen.openapi.yaml` | `app/<svc>/service/cmd/server/assets/openapi.yaml`(embed + 后置的 frontendgen 用) |
| TS / Dart / Java | `buf.gen.{ts,dart,java}.yaml`(模板预置,默认注释) | **外置模式:写回公共目录自己的 `gen/<lang>/`**(公共仓管版本、发自己的包,真正做到多语言共用一份源);默认模式:写项目内(与 gow 行为一致) |

- `wind api` 沿用 gow 的扫描行为:遍历 `proto_dir` 下全部 `*.gen.yaml` 逐个执行;`--lang go,ts` 可过滤
- **生成时可指定 proto 路径**:`wind api --path <file|dir> [--path <file|dir>...]`——
  - 无 `--path`:全量生成(gow 现行为,CI 用)
  - 有 `--path`:只生成指定的 proto 文件/目录(透传 buf 的 `--path` 过滤),**增量生成**(改哪个生成哪个)
  - 路径写法任意:相对当前目录/绝对路径均可,CLI 内部归一为「相对当前 workspace 根」再传给 buf;
    配合外置模式即可直接指定公共目录里的某个 proto 文件或子目录
- 消费方式:外置模式下其他语言直接引公共目录的生成物;Go 项目之间通过 `api/gen/go` + 各自 module 路径消费

**3)命令行为矩阵(官方命令与 wind 命令的分工)**

| 操作 | 默认模式 | 外置模式 |
|---|---|---|
| 新增 proto 文件 | 官方 `kratos proto add api/<...>/x.proto` 直接用 | **`wind proto add <相对proto_dir路径>`**:同内容模板自生成——官方命令虽接受任意路径,但包名从路径段推导,绝对路径会把盘符拼进包名(实测源码 `cmd/kratos/internal/proto/add/add.go`),且它不感知 buf workspace 约定 |
| proto → Go 代码 | 官方命令或 `wind api` 均可 | `wind api`(workspace 与 `-o` 按外置模式适配);两种模式都支持 `--path <file\|dir>` 指定 proto 文件/目录做增量生成 |
| CRUD 生成写 proto | `wind generate` 第 2 步:写到 `proto_dir`(两种模式同一逻辑,只是路径不同) | 同左 |

> 设计底线:`wind proto add` / `wind generate` 生成的 proto **内容、包名、布局在两种模式下逐字节一致**,
> 业务 proto 在「项目内 ↔ 公共目录」之间迁移零成本;`.scaffold.yaml` 是唯一需要动的地方。

### 4.1 命令面

| 命令 | 来源 | 说明 |
|---|---|---|

**模板来源(`wind new`,优先级 `--template` > `-r` > 默认):**

### 4.2 CRUD 生成链(gow 引擎原样保留)

```
wind generate --dsn <src> --service <svc> -d ent|gorm -t <tables>
  源(第一期):SQL 文件/内联 DDL、ent://schema 目录        ← schemasource 两源
  源(后置):mysql:// 活库、postgres://、gorm://model 目录  ← 再开三源

  1. schemasource → atlas schema.Table(统一表模型,类型映射:mysql.go 规则表)
  2. proto:<module>/service/<version>/<snake>.proto(CRUD: List/Count/Get/Create/Update/Delete/BatchCreate
     + FieldMask + 分页 + openapi 注解;字段全 optional 以支撑 SetNillable)
  3. ORM:ent → entimport 写 internal/data/ent/schema(含格式化)
        gorm → gorm.io/gen 写 model+DAO(gorm:// 源做 DAO 回转,只补不覆盖)
  4. data 层:internal/data/client/{ent,gorm}_client.go + internal/data/<model>_repo.go
     (repo 包装 go-crud 泛型仓储:ent → `entCrud.Repository`,gorm → `gormCrud` DAO,见 §4.4)
  5. service 层:internal/service/<model>_service.go
  6. server 层:internal/server/{grpc,rest}_server.go —— **已存在且有锚点 → 只做锚点注入,不动手写内容**
  7. 装配:cmd/server/wiring.go —— 四层分节锚点登记(register:repo/client/service/param/route/grpc-arg/rest-arg)
  8. 后处理:gofmt → wind api(buf)→ go build ./app/<svc>/...
     ★ 任一步失败:回滚本次生成文件 + 打印定位(内置,吸取 gow「生成完不能编译」教训)
```

### 4.4 repo 层与 go-crud 集成(已定,2026-11-07)

**决策:沿用 `tx7do/go-crud`,不自写 helper。** 依据(2026-11-07 实测 proxy.golang.org):
`entgo v0.0.55~v0.0.57`、`gorm v0.0.26`、`api v0.0.7` 的 `go.mod` 均无任何 `go-kratos` 依赖,
不会把 kratos/v2 拖进依赖图;entgo 的 `Repository[E]` 提供 ~24 个泛型方法
(List/Count/Get/Create/Update/Delete/BatchCreate + FieldMask + 分页 + 缓存/审计/多租户 viewer),
自写等价物至少 1-2d 且要长期维护。

**集成规则(四条,写进模板与 doctor 检查):**

1. **版本集中 pin 在 `deps.go`**:
   ```go
   GoCrudEntgo = "github.com/tx7do/go-crud/entgo@v0.0.57"
   GoCrudGorm  = "github.com/tx7do/go-crud/gorm@v0.0.26"
   GoCrudAPI   = "github.com/tx7do/go-crud/api@v0.0.7" // 分页 proto 的 Go 生成物
   ```
2. **分层铁律:go-crud 只允许 import 于 `internal/data/**`**(repo 层内部),
   service/biz/server 层只依赖 repo 接口。将来若要换自写 helper,只改 repo 模板 + go.mod,业务层零感知。
   `wind doctor` 增加 AST/文本扫描检查:非 `internal/data` 路径出现 `tx7do/go-crud` → FAIL。
3. **Go 版本要求**:go-crud `go` 指令为 **1.26.4** → 生成项目 `go.mod` 统一 **`go 1.26.4`**
   (kratos v3 只要求 1.25.0,取两者较大值;本机 toolchain 1.27.1 已满足)。
   这覆盖 kratos-v3.md §5.0 旧的「产出项目固定 1.25.0」说法。
4. **分页 proto 双轨**:proto 侧 buf dep `buf.build` 的 pagination 模块(模板 `buf.yaml` 已有),
   Go 侧 import `github.com/tx7do/go-crud/api/gen/go/pagination/v1`——与 gowind 现行用法一致,原样保留。

**退出预案**(未来 go-crud 若回归引入 kratos 依赖,或停更):
锁死当前版本 + repo 模板换成自写薄 helper(接口签名保持 `List/Get/Create/Update/Delete/...` 不变),
只需改模板与 `deps.go`,一次重新 `wind generate` 即完成切换。这也是分层铁律(第 2 条)的意义。

## 7. 风险与注意
