## 一、功能与职责（总）

### 1.1 功能定位

协议层（`xianyu/` 包）是客户端与闲鱼服务端之间的**唯一通道，可替换的隔离边界**：上层 `services/` 只依赖抽象接口 `XianyuProtocol`，对协议变更零感知。实现上**直接复用** `zhinianboke/xianyu-auto-reply` 的纯 Python 协议实现（HTTP 接口封装 + WS 长连接 + 消息编解码），项目整体采用 AGPL-3.0。

对上层暴露的能力（对应 [《客户端技术方案.md》](../客户端技术方案.md) §6.5 闲鱼客户端的定义）：封装开源逆向 SDK；提供 **cookie 验证、拉取账号信息、拉取商品列表、发送消息、WebSocket 连接** 五类能力；cookie 本地存储时加密、使用时解密（加密机制见 [技术方案-客户端-Cookie管理与加密](技术方案-客户端-Cookie管理与加密.md)）。

> 模块命名采用 `xianyu/` 独立包（`client.py` 承担 HTTP 部分、`session.py` 承担 WS 部分），不采用旧版的单文件 `goodfish_client.py`。

### 1.2 职责边界

| 负责 | 不负责 |
|---|---|
| Cookie 验证、拉取账号信息、拉取商品列表（HTTP） | 自身消息过滤（由消息流水线处理，见 [技术方案-客户端-消息处理流水线](技术方案-客户端-消息处理流水线.md)） |
| WS 长连接：握手 / reg / ackDiff / 心跳 / 重连 / token 失效自愈 | 消息业务处理（去重、窗口合并、AI 请求） |
| 推送解密与字段解析（codec） | 监听上限与启停编排（ListenManager，见 [技术方案-客户端-WebSocket监听](技术方案-客户端-WebSocket监听.md)） |
| Token 刷新与缓存（本地 SQLite 实现，不引入 Redis） | Cookie 加密存储与密钥管理（见 [技术方案-客户端-Cookie管理与加密](技术方案-客户端-Cookie管理与加密.md)） |
| 过滑块接口预留（本期不接，改上报"需人工处理"） | MySQL / Redis / Playwright 等上游基础设施（原则：**只搬协议层，不搬它的基础设施**） |

### 1.3 与其他模块的关系

| 对象 | 方向 | 交互方式 |
|---|---|---|
| 闲鱼服务端 | 下游 | HTTP（mtop 类接口）+ `wss://wss-goofish.dingtalk.com/` 长连接 |
| WebSocket 监听（XianyuLive） | 上游 | 每个监听账号一个连接实例，消费 `messages()` 异步流 |
| Cookie 管理 | 上游 | 提供解密后的 Cookie；验证结果回写账号有效性 |
| 商品同步 | 上游 | `fetch_items` 提供商品全量拉取 |
| 上游开源仓库（zhinianboke/xianyu-auto-reply，AGPL-3.0） | 上游 | 复用源码，保留版权头 + LICENSE 副本 + commit SHA（`xianyu/UPSTREAM.md`） |

## 二、逻辑实现（分）

### 2.1 总体设计与许可证决策

**项目整体采用 AGPL-3.0，协议层直接复用成熟开源实现，不再自研。**

| 项 | 说明 |
|---|---|
| **决策依据** | 协议逆向成本高、闲鱼随时变更协议；复用经大量真实验证的实现，工期与风险都显著低于自研 |
| **代价** | AGPL 具传染性：**Electron 客户端 + Python 本地服务 + 云端 RuoYi + Go llm-manage 整体都受 AGPL 约束** |

**AGPL-3.0 合规义务（必须执行）**：

| 义务 | 具体要求 |
|---|---|
| 提供完整源码 | 通过网络提供服务时，使用者有权获取完整对应源码（含我们的修改）；需在应用内提供源码获取入口 |
| 保留版权声明 | 复用文件保留原始版权头、LICENSE 副本与出处（仓库地址 + commit SHA） |
| 同许可分发 | 我们的衍生作品继续以 AGPL-3.0 分发 |
| 传染范围 | RuoYi-Cloud-Plus（MIT）等第三方库与 AGPL 代码合并后，**整体按 AGPL 分发** |
| 不豁免平台风险 | AGPL 只解决版权问题，**不解决闲鱼平台服务条款与账号风控风险**（两件事，需分别评估） |

> **顺带绕开一个坑**：协议逆向源头 `cv-cat/XianYuApis` **根目录无 LICENSE 文件**（GitHub API `license = null`），属默认保留所有权利、不可使用。改用下游**有正式 AGPL 许可证**的仓库即可规避，无需依赖它。

**选 `zhinianboke` 的决定性理由**：

1. **协议层是纯 Python** —— 已核实其 `backend-web` 依赖表中**没有 execjs / Node / protobuf / blackboxprotobuf**，IM 全链路纯 Python，**无需打包 Node 运行时，安装包不受影响**；
2. 体量适中（主文件 50KB vs 914KB 巨石），可整体抽离；
3. 模块边界天然贴合我们的 `xianyu/` 包（客户端 / 解析器 / 会话管理三者分离）；
4. 维护最活跃（2026-09 仍有推送）、社区最大（7.4k star）。

### 2.3 复用清单与已核实的协议事实

**直接采用的部分（映射到我们的 `xianyu/` 包）**：

| 我方文件 | 复用来源 | 职责 |
|---|---|---|
| `xianyu/session.py` | `chat_new/im_client.py` → `GoofishImClient` | WS 连接 / 注册 / 心跳 / 收发 / 重连 |
| `xianyu/codec.py` | `chat_new/push_message_parser.py` → `PushMessageParser` | 推送解密与字段解析 |
| `xianyu/constants.py` | 上述文件的模块级常量 | `WS_URL` / `app-key` / lwp 报文模板 / 字段路径 |
| `xianyu/utils.py` | `common/utils/xianyu_utils.py` | `generate_mid` / `generate_uuid` / `generate_device_id` / `trans_cookies` |
| `xianyu/protocol.py` | 本项目自研（薄适配层） | 抽象接口，见 §2.5 |

**已核实的协议技术事实（供评审与排障）**：

| 环节 | 事实 |
|---|---|
| IM 通道 | `wss://wss-goofish.dingtalk.com/`（闲鱼私信实际走钉钉 IM PaaS） |
| WS 超时设计 | `ClientTimeout(total=None, connect=30, sock_connect=30, sock_read=None)`，避免长连接被超时掐断；不依赖 aiohttp 库层心跳（`heartbeat` 关闭） |
| 应用层心跳 | 每 **15s** 发 `{"lwp":"/!"}`（**已裁定统一为 15s 节奏**） |
| 连接注册（四步） | ① HTTP 取 IM token → ② `/reg`（`app-key=444e9908a51d1cb236a27862abc769c9`、token、did、ua、wv、sync、mid）→ ③ `/r/SyncStatus/ackDiff` 报位点 → ④ **注册后 `sleep(3)`** 防 IM 流控（错误码 `400600001`） |
| 下行 ACK | 每帧必回 `{"code":200,"headers":{mid,sid}}`，并回显 `app-key` / `ua` / `dt`；**漏发会掉线** |
| 请求-响应配对 | `_pending: {mid: Future}`；`code == 200 or "body" in msg` 视为成功，否则抛 `ImRequestRejected` |
| 推送解析链路 | `body.syncPushPackage.data[]` → `PushMessageParser.decrypt_push_data()` → `.parse()` → 回调 |
| 发文本 | `/r/MessageSend/sendByReceiverScope`，`content.custom.data = base64(json({contentType:1, text:{text}}))` |
| 发图片 | 同上，`contentType:2` + `image.pics[{type:0, url, width, height}]`；URL 须为闲鱼 CDN 可访问地址（**协议事实，本期不接入**：AI 回复只发文字） |
| 撤回 | `/r/MessageManager/recallMessage` |
| 会话列表 | `/r/Conversation/listNewestPagination`（首页 `start_timestamp = 9007199254740991`） |
| 聊天记录 | `/r/MessageManager/listUserMessages`（`cid` 自动补 `@goofish`） |
| 流控退避 | `code == "400600001"` → 退避 `(attempt+1)*2` 秒，最多 3 次 |
| **token 失效识别** | `code == 400` 且无 body → 自动重连并换 token |
| **并发重连去重** | `_conn_generation` 连接代次 + `_reconnect_lock` 互斥锁，并发请求只重连一次 |
| **非幂等保护** | 发送 / 撤回在重连后**不自动重发**，主动抛错让上层决定，避免重复消息 |
| **Token 缓存隔离** | Redis 锁 + DB 表，TTL 6~15h 随机偏移；缓存键加 `chat_` 前缀与"自动回复连接"隔离，**防互踢** |
| 过滑块 | 委托独立 WebSocket 进程 `websocket_client.solve_captcha`（HTTP），含 9 项验证码关键词判定表 |

> 这套实现比自研起点高很多：**重连、流控退避、token 失效自愈、并发去重、非幂等保护、多连接隔离**都已具备，直接省掉协议层大部分自研工作量。

> 心跳已裁定：**统一为应用层每 15s 发 `{"lwp":"/!"}`**；断线以 WS 连接异常 / 接收异常感知（见 [技术方案-客户端-WebSocket监听](技术方案-客户端-WebSocket监听.md) §2.2），不再使用"30s 发送 / 10s 无响应判定"方案。

> 注：上游 Token 缓存的 Redis 锁 + DB 表形态在本地单机版替换为 SQLite 实现（见 §2.4 适配改造点 1~3）。

### 2.4 适配改造点（必须做，否则拿过来跑不起来）

复用的实现耦合了它自己的基础设施（MySQL / Redis / 独立过滑块进程），抽离时必须替换：

| # | 原实现耦合 | 适配方案 |
|---|---|---|
| 1 | `common.db.session.async_session_maker`（MySQL）查询 `load_token_api_mode(account_id)` | 抽象 `TokenApiModeProvider` 接口，注入我们的 SQLite 实现 |
| 2 | Token 缓存走 Redis + `xy_token_cache` 表 | 抽象 `TokenCacheStore` 接口；本地单机版用 SQLite，**不引入 Redis** |
| 3 | `token_request_lock`（账号级 Redis 分布式锁） | 换成 `asyncio.Lock`（单进程单账号，不需要分布式锁） |
| 4 | `_solve_captcha_via_websocket()` 依赖独立 WS 进程过滑块 | **本期不接**：改为上报"需人工处理"并标记账号异常（手动 Cookie 模式不触发滑块），仅预留接口 |
| 5 | `websocket_client.py` / `playwright` / `patchright` / `opencv-python-headless` | **不引入**（本期不做扫码 / 账密登录），避免 +300MB 浏览器内核 |
| 6 | SQLAlchemy / MySQL 模型与 `common/` 共享层 | 不引入，只搬协议层纯逻辑 |
| 7 | 日志使用 loguru | 与我们一致，直接复用 |

> **原则：只搬协议层，不搬它的基础设施。** `xianyu/` 包对外不暴露任何 SQLAlchemy / Redis / Playwright 类型。

**两处仍需我们自己处理的行为**：

| 行为 | 现状 | 处理 |
|---|---|---|
| **自身消息过滤** | 复用的 `im_client.py` 在收帧路径**不做** `sender_id == myid` 判断（`actualReceivers` 同时含自己，服务端会回推） | 放在 `services/message_pipeline.py` 步骤 2 处理（见 [技术方案-客户端-消息处理流水线](技术方案-客户端-消息处理流水线.md)），**不改动复用代码** |
| **重连后消息补拉** | 原实现在接通后固定上报 `pts = now, seq = 0`，断线窗口内的消息会丢 | 持久化 `pts` / `seq` 后从位点续传（本期 TODO，见 §七） |

**待核实的开放项** ★：商品列表（`fetch_items`）走 mtop 类 HTTP 接口，其签名实现**未在复用仓库中定位到**（可能在 `item_service.py` / `xianyu_publisher.py`）。**开发第 1 步必须先确认**；若确认不可用，退路是改用会话推送中携带的 `itemId` 增量沉淀商品数据（对商品同步的影响见 [技术方案-客户端-商品同步](技术方案-客户端-商品同步.md)）。

### 2.5 对外抽象接口

**抽象接口**（上层只依赖它，`services/` 层对协议变更零感知）：

```python
# xianyu/protocol.py —— 抽象接口：上层只依赖它，不依赖任何具体实现
from abc import ABC, abstractmethod
from typing import AsyncIterator


class XianyuAccountInfo:
    """账号信息（goodfish_id / nickname）。"""


class XianyuItem:
    """商品信息（item_id / title / desc / price / stock_status）。"""


class XianyuMessage:
    """消息（message_id / item_id / buyer_id / sender_id / content / type）。"""


class XianyuProtocol(ABC):
    """闲鱼协议抽象接口。所有方法异步、带超时、失败抛领域异常。"""

    @abstractmethod
    async def verify_cookie(self, cookie: str) -> XianyuAccountInfo: ...

    @abstractmethod
    async def fetch_items(self, cookie: str) -> list[XianyuItem]: ...

    @abstractmethod
    async def connect(self, cookie: str) -> None:
        """建立 WS 长连接（内部维护心跳）。"""

    @abstractmethod
    def messages(self) -> AsyncIterator[XianyuMessage]:
        """异步产出收到的消息（供流水线消费）。"""

    @abstractmethod
    async def send_message(self, item_id: str, buyer_id: str, content: str) -> bool: ...

    @abstractmethod
    async def close(self) -> None: ...
```

> 实现类 `XianyuHttpWsProtocol(XianyuProtocol)` 是**薄适配层**：内部持有复用的 `GoofishImClient`，把它的推送回调转成 `messages()` 异步流，把 `send_text_message` 包成 `send_message`。协议失效时只需替换实现类或同步上游修复，`services/` 层零改动。

> **本期只发送文本**：AI 回复一律为**文字**，不向买家发送图片。`send_message` 只实现文本发送；协议层虽具备发图片能力（见 §2.3），本期**不接入**。
