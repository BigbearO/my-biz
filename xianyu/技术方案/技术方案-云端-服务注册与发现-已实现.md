## 一、功能与职责（总）

### 1.1 功能定位

定义云端各服务在 Nacos 中的**注册契约与消费规则**：每个服务同时暴露 HTTP（北向）与 gRPC（东西向）两个端口，注册成**两个独立的 Nacos 服务**（`{app}` / `{app}-grpc`），Java、Go、Python 三侧使用同一套跨语言统一契约，保证互发现零障碍。

### 1.2 职责边界

- 本文只定义**跨语言的注册契约**（服务名、group、namespace、metadata、ephemeral、消费规则）
- 注册/发现的**具体实现**（可复用 Python 库 `xxs-nacos-grpc` 的设计、代码与验证清单）见[技术方案-云端-gRPC发现库xxs-nacos-grpc-已实现](技术方案-云端-gRPC发现库xxs-nacos-grpc-已实现.md)
- 服务调用矩阵、超时与身份透传约定见[技术方案-云端-架构总览](技术方案-云端-架构总览.md) §四

### 1.3 与其他模块的关系

- **网关**：用 `lb://{app}` 消费 HTTP 服务名（北向路由）
- **内部 gRPC 客户端**（对话服务、admin BFF）：订阅 `{app}-grpc` 服务名做东西向发现
- **Nacos 3.2**：注册中心 + 配置中心；namespace 按环境隔离是环境隔离的核心手段

## 二、逻辑实现（分）

### 2.1 双实例注册模型（双服务名）

每个服务**同时暴露两个端口**，因此**注册成两个独立的 Nacos 服务**（不是同一服务名下的两个实例）：

| Nacos 服务名 | port | 协议 | 消费方 |
|---|---|---|---|
| `{app}` | 8000 / 8080 | HTTP | 网关（北向 `lb://{app}`） |
| `{app}-grpc` | 9000 | gRPC | 内部服务（东西向，直连） |

例：`goodfish-item-service` / `goodfish-item-service-grpc`。

> **Go 侧实际命名（llm-manage，以实际为准）**：Go 服务经 kratos-bootstrap 本地定制 registry 注册，命名规则为 `{project}-{service}.{scheme}`（`/` 替换为 `-`，并追加 `.http` / `.grpc` scheme 后缀）。故 llm-manage 实际注册名为 **`good_fish_llm_manage-llm-service.http`**（REST :8899）与 **`good_fish_llm_manage-llm-service.grpc`**（gRPC :8999），与本文 `{app}` / `{app}-grpc` 的 Java 惯例不同。网关路由与 gRPC 客户端 target 必须按实际注册名配置（一字不差），例如网关 `/goodfish/llm/**` → `lb://good_fish_llm_manage-llm-service.http`，对话服务/消费方 → `nacos://good_fish_llm_manage-llm-service.grpc`。

### 2.2 注册契约

| 项 | 约定 |
|---|---|
| **服务名规则** | `{app}`（HTTP）/ `{app}-grpc`（gRPC），**后缀仅用于注册时推断 `metadata.protocol`** |
| **group** | `DEFAULT_GROUP` |
| **namespace** | 按环境隔离（`goodfish-dev` / `goodfish-test` / `goodfish-prod`） |
| **metadata** | `protocol`（http/grpc）、`secure`、`cluster`；可追加 `env`、`version` |
| **ephemeral** | `True`（临时实例，依赖客户端心跳保活；**不设 False**，否则 Nacos 会主动探 `healthUrl`） |
| **注册 IP** | 真实网卡 IP，**禁止 `0.0.0.0`** |

### 2.3 消费规则

- **网关**用 `lb://{app}` 消费 HTTP 服务名
- **内部 gRPC 客户端**订阅 `{app}-grpc`，**只按服务名 + group + namespace 查询**，并在客户端做 `enabled and healthy` 过滤
- **发现侧不解析后缀、不按 metadata 过滤**——唯一的硬性要求是「提供方注册的服务名 == 消费方配置的服务名」，一字不差

### 2.4 反模式警告（不要用同一服务名 + metadata 过滤）

> **不要用"同一服务名 + `metadata.protocol` 过滤"的方案**：gRPC 客户端无法在 target 里表达 metadata 条件，会退化成"查到 HTTP 实例却发现端口不通"，且订阅侧过滤逻辑各语言实现不一致，极易踩坑。

### 2.5 跨语言统一注册契约

与 §2.2 约定一致，此为 Java / Go / Python 三侧对齐后的完整版本：

| 项 | 约定 | 说明 |
|---|---|---|
| **HTTP 服务名** | `{app}`（Java/xxs 侧）；`{project}-{service}.http`（Go/kratos 侧实际） | 例：`goodfish-ai-service`、`template-provider`；Go 侧例：`good_fish_llm_manage-llm-service.http` |
| **gRPC 服务名** | `{app}-grpc`（Java/xxs 侧）；`{project}-{service}.grpc`（Go/kratos 侧实际） | 例：`goodfish-item-service-grpc`；Go 侧例：`good_fish_llm_manage-llm-service.grpc` |
| **后缀作用** | **仅注册时**用于推断 `metadata.protocol` | 发现侧**不解析后缀**，只按服务名查 |
| **group** | `DEFAULT_GROUP` | 可配置 |
| **namespace** | `goodfish-{env}` | 环境隔离核心 |
| **metadata** | `protocol` / `secure` / `cluster`（+ 业务可选 `env` / `version`） | 与 Java 侧键名一致 |
| **ephemeral** | `True` | 依赖 SDK 心跳；**不要设 False**（否则 Nacos 会探 `healthUrl`） |
| **发现过滤** | `healthyOnly` 语义 | 由客户端 `enabled and healthy` 实现 |
| **注册 IP** | 真实网卡 IP | **禁止 `0.0.0.0`** |

**唯一硬性要求**：

> 提供方注册的服务名字符串 == 消费方配置的服务名字符串，**一字不差**。

### 2.6 Python 侧本期范围

| 能力 | 是否启用 | 说明 |
|---|---|---|
| 注册 HTTP 实例 | ✅ | `goodfish-ai-service` |
| 注册 gRPC 实例 | ❌ | 本期 Python **不提供 gRPC 服务**，故不注册 `-grpc` |
