## 一、功能与职责（总）

### 1.1 功能定位

MessagePipeline（`services/message_pipeline.py`）是闲鱼消息从"收到 WS 原始帧"到"发出 AI 回复"的完整处理链路：**自身消息过滤 → 消息去重 → 消息过滤 → 滑动窗口合并 → 串行锁 + 全局并发闸 → 随机延迟 → 请求云端 AI → 发送回复 → 记录日志**。是"消息自动回复"需求的核心执行模块。

### 1.2 职责边界

| 负责 | 不负责 |
|---|---|
| 自身消息过滤（防止 AI 自问自答死循环） | WS 帧的协议解析与解密（协议层，见 [技术方案-客户端-闲鱼协议层](技术方案-客户端-闲鱼协议层.md)） |
| 消息去重（内存 LRU + SQLite 持久层） | 图片下载/转 PNG/上传（图片服务，见 [技术方案-客户端-图片处理](技术方案-客户端-图片处理.md)，流水线只调用） |
| 消息过滤（黑名单买家/系统号/关键词规则命中跳过 AI） | 云端 AI 服务的实现（见 [技术方案-云端-对话服务-AI回复编排](技术方案-云端-对话服务-AI回复编排.md)） |
| 滑动窗口合并（debounce）与批次组装（文本 + 图片） | 云端调用重试/401/403 的统一封装（cloud_client，见 [技术方案-客户端-云端调用与容错](技术方案-客户端-云端调用与容错.md)） |
| 并发控制（会话锁 + 全局 Semaphore）与随机延迟 | 日志存储表结构（见 [技术方案-客户端-本地存储与配置](技术方案-客户端-本地存储与配置.md)） |
| 调用闲鱼 WS 发送接口发送回复（含重试） | 监听启停与状态机（见 [技术方案-客户端-WebSocket监听](技术方案-客户端-WebSocket监听.md)） |

## 二、逻辑实现（分）

### 2.1 总体设计：十步处理流水线

```
收到闲鱼 WS 原始帧
    ↓
1. 协议解析
   解出 message_id / item_id / buyer_id / sender_id / 内容 / 类型
   非 IM 消息（系统事件、回执）走独立分支，不进入本流水线
    ↓
2. 自身消息过滤  ★关键
   sender_id == 当前监听账号 → 直接丢弃
   否则：本账号发出的回复会被回推，被当成"买家新消息"→ AI 自问自答死循环
   （根因：发消息时 actualReceivers 同时包含对方和自己，服务端会把自消息同步回来；
     复用的 im_client.py 在收帧路径不做此判断，需在本层补，见 技术方案-客户端-闲鱼协议层 §2.4）
    ↓
3. 消息去重
   基于 message_id：内存 LRU（默认 1000 条）+ SQLite 持久化最近 2000 条
   重启后仍能挡住重复帧；重复消息直接丢弃
    ↓
4. 消息过滤
   黑名单买家 / 系统号 / 关键词规则命中 → 跳过 AI 回复，仅记日志
   （规则引擎 TODO，当前仅内置黑名单）
    ↓
5. 滑动窗口合并（debounce）
   key = account_id + item_id + buyer_id
   窗口 5s（本地配置项）；窗口内新消息到达则重置计时器
   批次保留原始 messages[]（时间序）+ 拼接文本 + images[]
   图文合并，一起传给多模态模型
    ↓
6. 并发闸门
   每会话 asyncio.Lock：同一会话串行，避免回复乱序
   全局 asyncio.Semaphore（默认 10）：防止窗口集中到期时打爆云端
    ↓
7. 随机延迟  ★位置在「请求云端之前」
   1-2 秒随机延迟（A29），模拟真人"看到消息 → 想一下 → 再回复"的节奏
    ↓
8. 请求云端 AI 接口（经网关转发）
   批内如有图片：先按 技术方案-客户端-图片处理 下载转 PNG 并 POST /api/ai/image 上传拿 URL（失败降级 [图片]）
   POST /api/ai/reply，Header 带 Authorization: Bearer <token>
   携带：request_id（幂等键）、goodfish_item_id、buyer_id、goodfish_account_id、
         合并后的消息（含上传后的图片 URL）
   ├─ code=0       → 进入步骤 9
   ├─ 40401/50001  → 不回复，记日志（A30）
   ├─ 50301/超时   → 重试 3 次（2-3s 随机），仍失败进入"仅监听不回复"模式（A21）
   ├─ 401 / 40101  → 删除 token + 通知 Electron 跳转登录页（A27，见《客户端监听.md》§1.5.3）
   └─ 403 / 40301  → 删除 token + 停止监听 + 冻结应用（A42，见《客户端监听.md》§1.5.4）
    ↓
9. 发送回复  ★收到回复后立即发送，不再延迟
   调用闲鱼 WebSocket 发送接口
   失败重试 3 次，间隔 2-3s 随机；3 次失败 → 仅记本地日志，不上报云端（A19）
    ↓
10. 记录系统日志
   消息收发、AI 请求/响应、错误异常（A34）
```

> 关键参数已裁定（均取较新方案）：
> - **去重容量**：内存 LRU 1000 条 + SQLite 持久化 2000 条；
> - **窗口分组键**：`account_id + item_id + buyer_id`；
> - **随机延迟位置**：请求云端之前延迟、发送不再延迟（见 §2.2）。

### 2.2 随机延迟：放在「请求云端之前」

1-2 秒随机延迟（A29）位于步骤 7（请求云端之前），模拟真人"看到消息 → 思考 → 回复"的节奏；**发送环节（步骤 9）不做任何延迟**。

设计依据：延迟发生在客户端本地，与云端 LLM 计算是先后关系但不占用云端连接；拟真与风控效果不变的同时，端到端耗时更短、云端占用更少（响应后延迟会把等待叠加在 LLM 之后，白白拉长总耗时，还可能与网关超时预算叠加）。

> 备注：早期"收到回复后延迟"方案已作废，现行即"请求前延迟"。

### 2.3 幂等键 `request_id`

步骤 8 会重试，若服务端已处理但响应丢失，重试会造成**重复生成回复 + 重复落对话历史**。客户端按 `account_id + item_id + buyer_id + 批次最后一条 message_id` 生成稳定 `request_id`，云端按此键去重（云端幂等设计见 [技术方案-云端-对话服务-接口与幂等](技术方案-云端-对话服务-接口与幂等.md)）。`request_id` 同时落入 `message_log.request_id` 便于排障。

### 2.4 并发模型实现骨架

```python
# services/message_pipeline.py
import asyncio
from collections import OrderedDict


class ConversationWorker:
    """单个会话（account+item+buyer）的窗口合并与串行执行。"""

    def __init__(self, key: str, window_seconds: float,
                 gate: asyncio.Semaphore, handle_batch) -> None:
        self._key = key
        self._window = window_seconds
        self._gate = gate                  # 全局并发闸门
        self._handle_batch = handle_batch
        self._buffer: list[dict] = []
        self._timer: asyncio.TimerHandle | None = None
        self._lock = asyncio.Lock()        # 本会话串行锁

    async def push(self, message: dict) -> None:
        async with self._lock:
            self._buffer.append(message)
            self._reset_timer()

    def _reset_timer(self) -> None:
        if self._timer is not None:
            self._timer.cancel()
        loop = asyncio.get_running_loop()
        self._timer = loop.call_later(
            self._window,
            lambda: asyncio.create_task(self._flush()),
        )

    async def _flush(self) -> None:
        async with self._lock:
            batch, self._buffer = self._buffer, []
        if not batch:
            return
        async with self._gate:             # 全局限流后再打云端
            await self._handle_batch(self._key, batch)


class MessageDedup:
    """message_id LRU，内存层；持久层见 技术方案-客户端-本地存储与配置 dedup_record 表。"""

    def __init__(self, capacity: int) -> None:
        self._capacity = capacity
        self._seen: OrderedDict[str, None] = OrderedDict()

    def is_duplicate(self, message_id: str) -> bool:
        if message_id in self._seen:
            self._seen.move_to_end(message_id)
            return True
        self._seen[message_id] = None
        if len(self._seen) > self._capacity:
            self._seen.popitem(last=False)
        return False
```

> 会话 worker 用**固定分片**（`key → hash % N`）而不是字典直存，保证长时间运行不会因会话数增长而内存泄漏。

## 三、数据设计

- **去重持久层**：`dedup_record` 表（`message_id` 主键 + `created_at`，仅保留最近 2000 条 / 7 天），保证重启后仍能挡住重复帧；
- **消息日志**：`message_log` 表（`direction` in/out、`result` success/failed/skipped、`request_id` 等），记录买卖消息与 AI 回复；
- 表结构见 [技术方案-客户端-本地存储与配置](技术方案-客户端-本地存储与配置.md) §三。

## 五、异常与容错

| 异常场景 | 处理策略 |
|---|---|
| **自身消息回推**（收到自己发出的消息） | 步骤 2 直接丢弃（DEBUG 级记录），不进入 AI 流程，杜绝自问自答死循环 |
| **重复消息帧** | 步骤 3 去重丢弃（内存 LRU 1000 + SQLite 2000） |
| **命中过滤规则** | 黑名单买家/系统号/关键词 → 跳过 AI 回复，仅记日志 |
| **云端返回 40401（商品不存在）** | 不回复，记日志（A30） |
| **云端返回 50001（大模型调用失败）** | 不回复（降级策略 TODO，见 §七） |
| **云端返回 50301 / 请求超时** | 重试 3 次（2-3s 随机），仍失败进入"仅监听不回复"模式（A21） |
| **云端返回 401 / 40101** | 删除 token；渲染层经 `/api/system/status` 轮询到登录态过期标记后跳转登录页，不自动重登；监听保持运行（A27） |
| **云端返回 403 / 40301** | 删除 token + 停止所有监听 + 弹窗"授权已过期" + 冻结应用，只允许退出（A42） |
| **发送回复失败** | 重试 3 次（间隔 2-3s 随机）；3 次失败仅记本地日志，不上报云端（A19） |
| **图片下载/上传失败** | 该图替换为 `[图片]` 占位，仅上报文本部分，不阻断流程（见 [技术方案-客户端-图片处理](技术方案-客户端-图片处理.md)） |
