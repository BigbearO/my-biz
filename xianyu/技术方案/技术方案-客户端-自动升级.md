# 技术方案-客户端-自动升级

> 来源：[《客户端技术方案.md》](../客户端技术方案.md) §8.3 自动升级（内容重组收录，原文件保留未动）
> 关联：[需求-客户端-设置与自动升级](../需求/需求-客户端-设置与自动升级.md)

## 一、功能与职责（总）

### 1.1 功能定位

Electron 主进程（`electron/updater.js`）基于 **electron-updater** 实现客户端自动升级：检查更新 → 按强升/非强升弹出更新交互 → **停止所有进程 → 整体替换文件 → 重启**。升级粒度为**整体替换**：Electron + Python 一起升级（Python 产物已作为 extraResource 打进安装包，见 [技术方案-客户端-项目结构与打包](技术方案-客户端-项目结构与打包.md)）。

### 1.2 职责边界

| 负责 | 不负责 |
|---|---|
| electron-updater 检查更新与安装包下载 | 更新包的构建与发布（CI/云端文件存储侧） |
| 强升/非强升的更新交互弹窗 | 版本号判定逻辑（云端版本检查接口返回，见 [技术方案-云端-架构总览](技术方案-云端-架构总览.md)） |
| 升级前停止所有进程（含 Python 监听）、替换文件、重启 | Python 进程日常守护（见 [技术方案-客户端-本地服务进程管理](技术方案-客户端-本地服务进程管理.md)） |
| 本地 `/api/system/check-update` 接口暴露 | 用户数据迁移（数据目录 `%APPDATA%/goodfish` 在升级后保留） |

### 1.3 与其他模块的关系

| 对象 | 方向 | 交互方式 |
|---|---|---|
| 云端版本检查接口 | 下游 | `GET /goodfish/version/check` 检查新版本 |
| 本地 API | 下游 | 渲染层经 `/api/system/check-update` 触发检查更新 |
| 进程管理（python-manager） | 下游 | 升级时停止所有进程（含 Python 本地服务与全部监听） |
| 打包（electron-builder） | 上游 | 升级载体为 NSIS 安装包，整体替换 |

## 二、逻辑实现（分）

### 2.1 总体设计

- 使用 **electron-updater**；
- 升级为**整体替换**：Electron + Python 一起升级；
- 升级时**停止所有进程，替换文件，重启**。

### 2.2 检查更新

- 云端检查更新接口：`GET /goodfish/version/check`；
- 本地暴露接口：`/api/system/check-update`（渲染层设置页入口，见 [技术方案-客户端-本地API](技术方案-客户端-本地API.md) §四）。

### 2.3 强升与非强升

| 类型 | 交互 |
|---|---|
| **强升** | 只有"立即更新"按钮（不允许跳过） |
| **非强升** | "立即更新" + "以后再说" |

### 2.4 升级流程

```
检查更新（/goodfish/version/check）
    ↓
有新版本 → 按强升/非强升弹出更新交互
    ↓
用户确认更新
    ↓
停止所有进程（含 Python 本地服务，先停止所有监听）
    ↓
替换文件（整体替换安装包内容）
    ↓
重启应用（升级后不自动恢复监听，A25）
```

## 四、接口设计

| 接口 | 方法 | 说明 |
|---|---|---|
| /goodfish/version/check | GET | 云端检查更新接口（返回是否有新版本） |
| /api/system/check-update | GET | 本地检查更新入口（渲染层调用） |

## 五、异常与容错

| 异常场景 | 处理策略 |
|---|---|
| 升级时应用正在运行 | 升级前停止所有进程（Electron 先调 `/api/account/stop-all` 再退出，见 [技术方案-客户端-本地服务进程管理](技术方案-客户端-本地服务进程管理.md)） |
| 升级重启后 | 不自动恢复监听，需用户手动启动（A25，见 [技术方案-客户端-WebSocket监听](技术方案-客户端-WebSocket监听.md)） |
| 用户数据保留 | 数据目录固定 `%APPDATA%/goodfish`，整体替换只覆盖安装目录，用户数据不受影响 |
