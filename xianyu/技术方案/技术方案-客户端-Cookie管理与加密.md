# 技术方案-客户端-Cookie管理与加密

> 来源：[《客户端监听.md》](../客户端监听.md) §2.5 Cookie 管理、§2.13 凭证加密与密钥管理（内容重组收录，原文件保留未动）
> 关联：[需求-客户端-安全与本地配置](../需求/需求-客户端-安全与本地配置.md)

## 一、功能与职责（总）

### 1.1 功能定位

CookieManager 负责闲鱼 Cookie 的全生命周期：**添加验证 → 加密落库 → 使用时解密 → 有效性检测 → 失效处理 → 删除确认**。Cookie 是客户端访问闲鱼的唯一凭证，属于最高敏感级数据：只在本地加密存储（AES-256-GCM，SQLite），**永不上传云端**（A10）。

### 1.2 职责边界

| 负责 | 不负责 |
|---|---|
| Cookie 加密存储（AES-256-GCM，SQLite）与使用时解密 | 监听启停编排（由 ListenManager 完成，见 [技术方案-客户端-WebSocket监听](技术方案-客户端-WebSocket监听.md)） |
| 主密钥管理（DPAPI / 机器指纹派生）与加解密实现（`core/crypto.py`） | 密文表结构定义（见 [技术方案-客户端-本地存储与配置](技术方案-客户端-本地存储与配置.md)） |
| 有效性检测（开始监听时 + 运行时每小时）与失效检测（WS 消息/请求 401） | 用 Cookie 收发消息（由协议层完成，见 [技术方案-客户端-闲鱼协议层](技术方案-客户端-闲鱼协议层.md)） |
| 脱敏展示（列表页前 4 后 4）与"永不上云"边界 | 云端管理后台的账号体系（登录 token 见 [技术方案-客户端-云端调用与容错](技术方案-客户端-云端调用与容错.md)） |

### 1.3 与其他模块的关系

| 对象 | 方向 | 交互方式 |
|---|---|---|
| 账号服务（添加/删除账号） | 上游 | 添加时先调闲鱼接口验证 Cookie，通过后自动拉取闲鱼 ID/昵称 |
| WebSocket 监听 | 下游 | 建连/重连时提供解密后的 Cookie；失效检测回调触发停听 |
| 闲鱼协议层 | 下游 | cookie 验证、拉取账号信息由协议层 HTTP 接口完成（本地存储时加密，使用时解密） |
| 本地存储 | 下游 | 密文写入 `goodfish_account.cookie` 字段；主密钥密文存 `%APPDATA%/goodfish/master.key` |

## 二、逻辑实现（分）

### 2.1 总体设计

Cookie 生命周期链路：

```
用户粘贴 Cookie（手动输入框，一次一个）
    → 调闲鱼接口验证（协议层 verify_cookie）
    → 验证通过自动拉取闲鱼 ID/昵称
    → 同一闲鱼 ID 去重校验（只允许一条记录，A11）
    → AES-256-GCM 加密后落 SQLite（永不上云，A10）
    → 开始监听时验证（A7）+ 运行时每小时巡检
    → 失效：停止监听 + 标记失效 + 弹窗提示
    → 删除：监听中的账号需确认，先停监听再删（A26）
```

### 2.2 Cookie 管理方案

| 功能 | 方案 |
|---|---|
| **本地存储** | SQLite 存储，AES-256-GCM 加密，**永不上传云端**（A10） |
| **字段** | id、goodfish_id、goodfish_nickname、cookie（加密）、备注、有效性、监听状态、创建时间 |
| **添加方式** | 手动输入框输入，一次一个；先调闲鱼接口验证，通过后自动拉取闲鱼 ID/昵称 |
| **账号去重** | 同一闲鱼 ID 只允许一条记录（A11） |
| **脱敏显示** | 列表页脱敏，点详情查看完整（A5） |
| **有效性检测** | 开始监听时验证（A7）+ 运行时每小时检测 |
| **失效处理** | 弹窗提示"Cookie 已失效"，不提供重新输入入口（用户去账号管理页处理） |
| **监听控制** | 每条记录"开始监听/停止监听"，同时最多 N 个账号（N 可配置，默认 3，A6） |
| **删除确认** | 监听中的账号删除需确认，先停监听再删（A26） |

### 2.3 凭证加密与密钥管理

| 项 | 方案 |
|---|---|
| **主密钥（Windows）** | 用 **DPAPI**（`CryptProtectData`，绑定当前 Windows 用户）加密随机生成的 32 字节主密钥，密文存 `%APPDATA%/goodfish/master.key` |
| **主密钥（跨平台兜底）** | 机器指纹（`machine-id` + 用户名）经 PBKDF2-HMAC-SHA256（迭代 200k + 随机 salt）派生，salt 存 `master.salt` |
| **数据加密** | 主密钥 + 每条记录随机 12 字节 nonce，AES-256-GCM；密文格式 `base64(nonce ‖ ciphertext ‖ tag)` |
| **明文生命周期** | 仅内存驻留，进程退出即释放；**日志、异常栈、上报字段一律不得包含明文 Cookie** |
| **脱敏规则** | 列表页前 4 后 4（A5）；云端上报只带 `goodfish_id` / `nickname`（A10） |

> 加密等 CPU/同步任务用 `asyncio.to_thread()` 卸载执行，避免阻塞事件循环卡住 WS 心跳（见 [技术方案-客户端-总体架构](技术方案-客户端-总体架构.md) §2.3）。

## 三、数据设计

密文落库于 `goodfish_account.cookie`（TEXT，AES-256-GCM 密文），表结构见 [技术方案-客户端-本地存储与配置](技术方案-客户端-本地存储与配置.md) §三。

## 五、异常与容错

| 异常场景 | 处理策略 |
|---|---|
| **Cookie 失效**（运行时检测到） | 停止监听 + 标记失效 + 弹窗提示，不提供重新输入（用户去账号管理页处理） |
| **Cookie 失效（WS/请求 401）** | 收到闲鱼服务端失效消息 / 请求返回 401 → 停止监听 + 标记失效 + 弹窗提示 |
| **主密钥解密失败** | 提示"凭证无法解密，请重新录入 Cookie"，**不静默清空**用户数据 |
| **启动时密钥校验** | 启动顺序第 4 步：解密主密钥，校验能否解开已存 Cookie（失败 → 提示重新录入，不静默） |
| **明文泄露防护** | 日志、异常栈、上报字段一律不得包含明文 Cookie；云端上报只带 `goodfish_id` / `nickname` |
