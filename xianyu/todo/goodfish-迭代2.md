## 一、开源项目调研

### 1.1 调研背景

迭代2需要实现自动发货、订单管理、商品擦亮等功能，这些功能都依赖闲鱼协议层的实现（WebSocket 监听、消息收发、Cookie 管理、商品/订单 API 调用）。迭代1已实现协议层基础能力（监听与回复），迭代2在此基础上扩展业务功能。

为避免重复造轮子，调研了三个主流开源闲鱼自动化项目，评估其在迭代2功能上的参考价值。

### 1.4 各项目参考价值

#### xianyu-auto-reply-fix（GuDong2003）— 最推荐参考

**优点**：
- 轻量级，SQLite + 单体，和本项目本地 Python 服务架构最接近
- 核心模块独立清晰：`cookie_manager.py`、`ai_reply_engine.py`、`message_filter_service.py`、`chat_event_hub.py`、`item_polish_module.py`
- AI 接口支持最丰富（6种），llm-manage 模块可参考其适配层设计
- 社区最活跃（2.7k Star），问题容易找到解决方案

**迭代1可参考模块**（监听与回复）：
- `cookie_manager.py` → Cookie 管理与刷新机制
- `chat_event_hub.py` → WebSocket 消息事件分发
- `message_filter_service.py` → 消息过滤与去重
- `ai_reply_engine.py` → 多模型适配层

**迭代2可参考模块**（发货/订单/擦亮）：
- `item_polish_module.py` → 商品擦亮实现
- `order_status_handler.py` → 订单状态处理
- `order_event_hub.py` → 订单事件分发
- `blacklist_service.py` → 黑名单/风险拦截

#### xianyu-auto-reply（zhinianboke）— 架构参考

**优点**：
- 架构最规范，微服务拆分清晰
- WebSocket 服务独立（端口8090），和本项目"本地只做监听"思路一致
- 有 Windows EXE 打包方案（Nuitka），可参考 Electron 嵌套 Python exe 的打包配置
- 技术栈最匹配（FastAPI + SQLAlchemy 2.0）

**迭代1可参考部分**：
- `websocket/` 服务 → WebSocket 监听服务的边界划分
- `launcher/` Windows 启动器 → 桌面端打包方案

**迭代2可参考部分**：
- `scheduler/` 定时任务服务 → 自动发货、擦亮的定时任务调度
- 公开 API 设计 → 客户端与云端的接口规范
- 订单拉取与状态跟踪实现

#### xianyu-super-butler（23Star）— 产品功能参考

**优点**：
- 功能最全面，UI 最现代化
- 产品设计成熟，可参考交互流程

**不足**：
- 功能太重，很多本项目不需要
- 基于 xianyu-auto-reply 二开，核心代码不如原项目清晰
- 代码参考价值较低

**迭代2可参考**：
- 发货规则的三级配置（全局/账号/商品）
- 经营看板的数据展示
- 买家互动的触发时机设计

### 1.5 调研结论

1. **主要参考 `xianyu-auto-reply-fix`**：其模块化结构和轻量架构最适合本项目本地 Python 服务，迭代1的监听与回复、迭代2的发货/擦亮都可参考其模块实现
2. **辅助参考 `xianyu-auto-reply`**：其 WebSocket 服务拆分（迭代1）和 scheduler 定时任务调度（迭代2）有借鉴价值
3. **super-butler 仅作产品参考**：不参考代码，只参考交互流程和功能设计
4. **AGPL-3.0 风险提示**：三个项目均为 AGPL-3.0 协议，**禁止商业用途**。本项目只能参考实现思路，不能直接复制代码，所有闲鱼协议层代码需自行实现或基于无版权风险的基础库

> **说明**：Cookie 管理、消息监听、AI 自动回复、商品同步等基础能力在迭代1实现，迭代2直接复用。

### 2.2 核心设计原则

**凡是需要调用闲鱼 API 的操作，执行都在客户端；凡是配置和数据，都存储在云端。**

原因：
1. Cookie 只存在客户端，不上云（安全）
2. 所有闲鱼 API 调用走本地 IP（防封号）
3. 配置和数据在云端，换设备/重装不丢失
4. 多设备统一管理，任意客户端上线即可执行任务

## 三、自动发货架构设计

### 3.1 整体架构

```
云端（管理/存储）                    客户端（执行）
┌──────────────────────┐           ┌──────────────────────┐
│ 发货规则管理          │  拉取规则  │ 订单状态监听          │
│  - 商品→卡密映射      │ ←───────→ │  - WebSocket 订单通知 │
│  - 全局/账号/商品级   │  上报结果  │  - 定时订单拉取补偿   │
│ 卡密库存管理          │           │ 发货规则匹配          │
│  - 卡券分组           │           │ 库存预占（云端）      │
│  - 库存导入/扣减      │           │ 闲鱼 API 调用         │
│  - 库存预警           │           │  - 发送卡密消息       │
│ 发货记录存储          │           │  - 确认发货           │
│  - 发货成功/失败记录  │           │ 结果上报              │
│  - 订单去重           │           │                      │
└──────────────────────┘           └──────────────────────┘
```

### 3.2 发货流程

```
买家付款
    ↓
客户端收到订单通知（WebSocket）
    ↓
查询云端发货规则（商品ID → 卡密分组）
    ↓
云端预占库存（扣减库存，生成发货任务，状态=待发货）
    ↓
客户端调用闲鱼 API 发送卡密消息
    ↓
发送成功？
    ├─ 是 → 上报成功 → 云端确认发货任务（状态=已发货）
    └─ 否 → 上报失败 → 云端回滚库存（状态=失败，可手动补发）
```

### 3.3 发货规则层级

优先级从高到低：
1. **指定商品 + 指定账号**：精确匹配
2. **指定商品 + 全局**：商品级规则
3. **指定账号 + 关键词匹配**：账号级关键词规则
4. **全局 + 关键词兜底**：全局兜底规则

### 3.4 关键设计

**库存预占机制**：
- 客户端匹配到规则后，先调用云端接口预占库存
- 预占成功才执行发货，避免超卖
- 发货失败时回滚库存
- 预占超时（比如5分钟）自动释放

**订单去重**：
- 以闲鱼订单 ID 为唯一键
- 同一订单只发货一次
- 客户端重启后拉取未完成任务，避免重复发货

**多客户端并发控制**：
- 云端任务锁：同一订单只能被一个客户端领取
- 客户端领取任务时加分布式锁，锁超时自动释放

**发货前风险拦截**：
- 黑名单买家不发货
- 异常订单（价格异常、地址异常）标记待人工确认
- 同一买家短时间内多单限制

## 四、订单管理架构设计

### 4.1 整体架构

```
云端（存储/查询）                    客户端（同步）
┌──────────────────────┐           ┌──────────────────────┐
│ 订单数据存储          │  上报订单  │ 定时拉取闲鱼订单      │
│  - 订单基本信息       │ ←───────→ │  - 全量同步（首次）   │
│  - 订单状态           │           │  - 增量同步（按时间） │
│  - 买家信息           │           │ 订单状态变更监听      │
│  - 商品信息           │           │  - WebSocket 通知     │
│  - 发货状态           │           │                      │
│ 订单查询界面          │           │                      │
│  - 列表/筛选/详情     │           │                      │
│ 手动发货/补发         │           │                      │
└──────────────────────┘           └──────────────────────┘
```

### 4.2 同步策略

**首次同步**：
- 全量拉取闲鱼历史订单（分页拉取，直到拉完）
- 写入云端，以订单 ID 去重

**增量同步**：
- 默认每 5 分钟拉取最近 1 小时的订单
- 有新消息/订单通知时立即触发一次同步
- 同步频率可配置

**数据去重**：
- 以闲鱼订单 ID 为主键
- 已存在的订单更新状态，不重复插入

### 4.3 订单状态映射

| 闲鱼状态 | 系统状态 | 触发动作 |
|---|---|---|
| 待付款 | 待付款 | - |
| 待发货 | 待发货 | 触发自动发货 |
| 已发货 | 已发货 | - |
| 已完成 | 已完成 | 触发自动评价/求花 |
| 已退款 | 已退款 | 标记，不发货 |
| 已取消 | 已取消 | 释放预占库存 |

## 五、商品擦亮架构设计

### 5.1 整体架构

```
云端（策略/存储）                    客户端（执行）
┌──────────────────────┐           ┌──────────────────────┐
│ 擦亮策略配置          │  拉取策略  │ 定时任务调度          │
│  - 哪些商品擦亮       │ ←───────→ │  - 按策略执行         │
│  - 擦亮间隔           │  上报日志  │  - 随机延迟模拟真人   │
│  - 允许时间段         │           │ 闲鱼 API 调用         │
│  - 每日上限           │           │  - 单个商品擦亮       │
│ 擦亮日志存储          │           │  - 批量擦亮（限流）   │
│  - 成功/失败记录      │           │                      │
│  - 擦亮时间统计       │           │                      │
└──────────────────────┘           └──────────────────────┘
```

### 5.2 防封号设计

商品擦亮是最容易触发风控的功能，必须做严格的限流和随机化：

1. **随机延迟**：策略配置的间隔是基础值，实际执行时 ±20% 随机浮动
   - 例：配置 2 小时擦亮一次，实际 1.6~2.4 小时随机
2. **时间段控制**：只在配置的时间段内擦亮（比如 9:00~23:00），深夜不操作
3. **每日上限**：每个商品每日擦亮次数上限（比如最多 3 次）
4. **并发限制**：同一账号同时只擦亮一个商品，擦亮间隔 5~10 秒随机
5. **失败退避**：擦亮失败时指数退避，不立即重试
6. **本地 IP**：必须在客户端执行，绝不用服务器 IP

### 5.3 擦亮策略

| 策略类型 | 说明 |
|---|---|
| 全部商品定时擦亮 | 账号下所有在售商品按间隔擦亮 |
| 指定商品擦亮 | 只擦亮选中的商品 |
| 按销量优先级 | 销量高/想要多的商品优先擦亮 |

## 六、客户端与云端通信协议

### 6.1 通信方式

- **配置拉取**：客户端启动时 + 定时（每小时）拉取最新配置（发货规则、擦亮策略）
- **任务领取**：客户端定时（每 30 秒）向云端轮询待执行任务
- **结果上报**：客户端执行完任务后立即上报结果
- **订单同步**：客户端定时拉取订单并上报

### 6.2 关键接口（规划）

| 接口 | 方向 | 说明 |
|---|---|---|
| GET /goodfish/shipping/rules | 客户端→云端 | 拉取发货规则 |
| POST /goodfish/shipping/lock | 客户端→云端 | 预占库存+创建发货任务 |
| POST /goodfish/shipping/confirm | 客户端→云端 | 上报发货结果 |
| POST /goodfish/orders/sync | 客户端→云端 | 上报订单数据 |
| GET /goodfish/polish/strategy | 客户端→云端 | 拉取擦亮策略 |
| POST /goodfish/polish/log | 客户端→云端 | 上报擦亮日志 |

## 七、异常处理

### 7.1 客户端离线

- 自动发货：客户端上线后拉取未处理订单，补发货（订单 ID 去重）
- 订单同步：上线后立即触发一次全量增量同步
- 商品擦亮：错过的擦亮任务不补执行，按下次计划时间执行

### 7.2 发货失败

- 云端标记发货任务为失败，回滚库存
- 支持手动补发（在云端订单详情页操作）
- 连续失败 3 次的账号标记异常，暂停自动发货

### 7.3 库存不足

- 发货任务标记为"库存不足"
- 发送通知提醒管理员补货
- 补货后可手动触发补发

### 7.4 云端不可用

- 客户端缓存配置和待发货任务（本地 SQLite）
- 云端恢复后同步数据
- 发货操作需要云端预占库存，云端不可用时暂停自动发货，只记录订单

## 八、迭代2 实施建议

### 8.1 实施顺序

1. **订单同步**（基础）：先把订单数据打通，为自动发货提供数据基础
2. **自动发货**（核心）：最有价值的功能，优先实现
3. **商品擦亮**（增值）：风控敏感，最后实现，需要充分测试
4. **买家互动**（可选）：自动评价/求花，优先级最低

### 8.2 风险提示

1. **AGPL-3.0 协议**：只能参考思路，不能复制开源项目代码
2. **闲鱼协议变更**：逆向接口随时可能失效，需要持续维护
3. **封号风险**：自动发货和擦亮都有封号风险，需要做好限流和随机化
4. **法律合规**：虚拟商品自动发货需遵守相关法律法规，卡密类商品需注意版权问题
